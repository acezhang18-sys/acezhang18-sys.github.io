Creating Learning Systems

Overview

I build learning as an operating system, not as a string of one-off explanations. A learning system has a target, a path, a way to see whether it worked, and a way for the next person to run it without me. The point is repeatable skill, not a memorable session.

Core Method

  • Start from the result the group actually needs, then design backward
  • Turn private know-how into a path other people can follow
  • Put feedback in the loop so errors get caught before they become culture
  • Make the material survive the original teacher: notes, drills, and ownership
  • Retire what does not transfer. If only I can run it, it is not a system yet

Relevant Experience

  • Pre-Selection leadership training — Evolved into a locus for aspirant-scale Foreign Internal Defense as well as low-stakes civilian leadership training; Special Forces hopefuls gained live, low-stakes experience developing other people, civilians gained simulated experience in leadership and community management. Guides made the path visible. Shadowing and mentorship remained the way leadership actually transferred.
  • ASVAB and accession prep — Built a diagnostic-to-drill loop from scores and practice data. Weak sections were isolated, trained, and retested. The method was reused across candidates instead of reinvented each session.
  • Team Echoes — Led by example and drove development, allowing apprentices and protégés to shadow my moves and learn via observation. Handoff became a simple matter of handing off pieces of the leadership infrastructure to those who had been trained into the role with nothing more than participation and honest discussion.
  • 38th and similar units — Standards, selection, and after-action habits were treated as teaching tools. People learned by running the room under live conditions, then hearing the hidden purpose of quiet moves after the fact.
  • Written transfer — Recurring failures from sales floors, community staff work, and high-rejection environments were turned into short reusable loops and actionable guidance material instead of left as folklore.

Method

Define the system
  • Name the outcome in one line.
  • List the few skills that actually produce that outcome.
  • Decide what “good enough to pass on” looks like.

Build the loop
  • Diagnose: short tasks that show knowledge gaps, load failures, or self-interference.
  • Train: one primary constraint per block.
  • Check: a score, a drill, a live problem, or a written recap the learner has to produce.
  • Capture: write the path the same day. Memory is not a system.
  • Hand off: the next person runs it. I watch for drift, I do not repossess the work.

Keep it alive
  • If the same question keeps returning, the system is incomplete.
  • If people only perform when I am present, ownership did not transfer.
  • If a guide cannot be used by a competent stranger, it is still a personal note.

What This Means for Clients / Collaborators

I can take a skill that currently lives in one person’s head and turn it into a working loop: diagnosis, practice, check, write-up, and handoff. Useful for onboarding, test prep, staff development, and any group that keeps paying the same teaching tax because nothing was ever made reusable.
